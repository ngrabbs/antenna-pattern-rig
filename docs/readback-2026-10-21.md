# Installed rotor firmware readback: 2026-10-21

## Result

Readback succeeded using a Docker-contained AVRDUDE 7.1 environment on the user's
Linux host. No software packages were installed on the host OS. Motor power was
disconnected before serial access. The existing application was not replaced.

- USB identification: Arduino Uno R3, VID:PID 2341:0043.
- MCU signature: 0x1e950f, ATmega328P.
- Bootloader transport: Arduino/STK500v1 at 115200 baud.
- Two independently opened bootloader sessions read 32768 flash bytes each.
- Binary comparison: identical.
- SHA-256 of each binary:
  `89b26f2317830ebda9cca516c632737e8bc875146ac70dbd081e1fe5be117ff7`
- An additional Intel HEX read passed independent record-length/checksum
  validation and reconstructed exactly the same 32768 bytes.
- The image contains plausible AVR reset vectors, nonblank program data, and
  embedded azimuth/elevation rotor command text. Under the standard Uno 512-byte
  boot-section assumption, non-FF application bytes extend through address 8115;
  this is an observation about the dump, not a recovered source/ELF program size.

Raw images, device identifiers, detailed logs and inspection output are retained
privately under ignored `backups/`; none are committed to this public repository.
A separate persistent copy was retained on the Linux host outside `/tmp`.

## What this establishes

The currently installed compiled flash program can be read. It does not recover
the original .ino, comments, symbol names, build flags or libraries. Embedded
command descriptions are evidence of rotor functionality, not proof that any
particular command is safe or that an upstream source repository is an exact match.

No application commands were sent. No diagnostic sketch, replacement firmware,
chip erase, fuse write, lock-bit write or EEPROM write was requested. Bootloader
connections reset the board; the application may resume after connection closes.

EEPROM calibration, fuse/lock state and restoration have NOT been verified.
The full HEX includes the flash address range containing the bootloader. Do not
blindly upload this full-range image through the bootloader; plan an appropriate
application-only or ISP restoration method and validate on a spare board if possible.

## Reproducible tooling

Build the tools in Docker, not the host:

```sh
docker build -t antenna-rig-readback:20261021 tools/readback
```

The actual read invocation used these AVRDUDE arguments (port/path are container
paths, and require deliberate device and backup-directory mounts):

```sh
avrdude -p atmega328p -c arduino -P /dev/arduino -b 115200 -n -A \
  -U flash:r:/backup/flash-a.bin:r -l /backup/read-a.log
```

A second session used `flash-b.bin` and additionally
`-U flash:r:/backup/flash-b.hex:i`. `-n` suppresses writes; `-A` retains trailing
0xFF data. Containers used only the identified Uno device, a backup-directory
mount, host user permissions plus the device's group, no network, dropped
capabilities and no-new-privileges. They were removed after exiting; the image
remains available for reuse. No existing host containers were stopped or changed.

The Dockerfile uses distribution package versions rather than immutable package
pins; future rebuilds may differ. This session used Ubuntu 24.04 and AVRDUDE 7.1.
